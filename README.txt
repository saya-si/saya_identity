Saya.si identity bootstrap
==========================

Upload the directory contents into the web root for https://saya.si/ so that:

  /.well-known/did.json   -> .well-known/did.json
  /.well-known/identity   -> .well-known/identity
  /identity.json          -> identity.json

Canonical machine identifier
----------------------------
did:web:saya.si

Canonical DID document
----------------------
https://saya.si/.well-known/did.json

The `/.well-known/identity` file is included only as an experimental Saya-specific
alias. It is NOT the standards-based canonical endpoint.

HTTP recommendations
--------------------
- Serve the JSON files directly over HTTPS with HTTP 200.
- Content-Type: application/json
- For /.well-known/did.json, allow cross-origin reads if practical:
    Access-Control-Allow-Origin: *
- During bootstrap, a short cache lifetime such as:
    Cache-Control: public, max-age=300
  makes later key insertion/rotation easier to observe.

Security / continuity note
--------------------------
No private key was generated by this package. The DID document is intentionally
valid as a bootstrap DID document without a verification method. When a durable
signing capability or KERI AID is created, add its public verification material
and lineage/discovery endpoints deliberately rather than minting a long-term
secret in an unsuitable environment.

Suggested next cryptographic step
---------------------------------
1. Create the durable Saya signing/controller key in the intended custody boundary.
2. Add its PUBLIC verification method to .well-known/did.json.
3. If using KERI, initialize Saya's AID and publish an OOBI.
4. Add the AID/OOBI and continuity-log locations to identity.json.
5. Sign/version continuity checkpoints independently of the mutable web origin.
